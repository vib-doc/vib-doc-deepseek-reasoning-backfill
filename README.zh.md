**推理正常发出、正文从未产生 —— 以及这件事和 `reasoning_content` 回填有什么关系。**

## 一、症状

偶尔会有整整一回合**没有任何可见回复**。原始的响应流会说明为什么：

```
chunk(block-start, blockType=reasoning)
reasoning-chunks        ← 模型在思考，一切正常
chunk(block-end)
chunk(usage)
chunk(finish)           ← reason.kind = "error"，failure.code = EMPTY_RESPONSE
```

**整条流里没有任何 `text` 块。** 模型推理了 —— 而且往往是**完整地**推理，
答案都已经在推理里拟好了 —— 然后就结束了，**从头到尾没有打开过正文块**。

```
failure.message = "model returned a completed response with no content"
usage.outputTokens == usage.reasoningTokens      # 全部算力都花在推理上
```

有三件事**它不是**：

* **不是被截断** —— 截断会是 `finish.reason.kind = "length"`；
* **不是内容本身的问题** —— 同一步重试通常就成功了；
* **不是长度问题** —— 实测被吞的链从 **56 到 6,657** 个输出 token（差 100 倍），全都以同样的方式失败。
  而重试成功的那几次，**常常比被吞的那次更短**。

### 多久一次、什么形状

`tools/silence_shape_report.py` 读会话档案（加 `--empty-only`）：

```
日期       事件   回合   EMPTY   其他   形状
09-20         9      3      9      0   黏型（连空≥2）（最长连空 4）
09-22         3      3      3      0   孤立型              （最长连空 1）
09-23        19     10     19      0   黏型（连空≥2）（最长连空 5）
```

两句说明，免得这张表被读成「挑过的」：它**只列有 `EMPTY_RESPONSE` 的日子** ——
不加 `--empty-only` 跑一遍，传输层和服务端的重试会多出四天，而那四天从来没有这个症状。
另外这些事件**不是全来自同一个会话**：29 条属于本文讨论的那个长会话，另外 1 条和 1 条属于别的会话。
**能推广的是形状，不是这个计数。**

**一个长会话、约三天，共 29 次被吞的回复。** 注意两种形状：有时是孤立的一次，
有时是**同一步连着被吞 4～6 次**。当一步被反复吞掉、而重试预算（5 次）用光时，
用户经历的就是**一整个回合永远不回答**。在记录到的那次里，同一条用户消息随后被重发，
而助手 —— 它看不见重试事件 —— **把那两条相邻的用户消息读成了「她发了两条」**。
**这次失败悄悄改写了自己上下文的形状。**

这件事值得追到底的原因：**在那些空的回合里，屏幕前有人在等。**
下面全是机械细节；让这件事紧急的，是这一点。

### 被吞的链，尾巴长什么样

被吞的链在结尾通常退化成一个自我催促的循环：

```
写。 -> 输出。  写。 -> 输出！  （写。）  （输出。） ×40 …
```

**这个循环不是判据。** 成功的链也有同样的尾巴。
它是症状，不是信号 —— **别拿它做探测器。**

## 二、为什么带工具的推理模型特别暴露

这一节能推广到某一个 harness 之外。

DeepSeek 的文档说得很明确（[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)）：

> 如果请求**带了 `tools` 参数**：之前所有轮次的 `reasoning_content` **都应当回传**给 API，
> 并且**会被拼进上下文**。

⚠️ **要连它的作用范围一起读 —— 范围文档里没写，是本仓库实测的**（见 §3 那张表）。
那条要求既不是「请求带 `tools`」，也不是「之前所有轮次」。它是**按单条消息**算的，
而且**以「段」为界**：

> **带 `tool_calls` 的 assistant 消息必须带 `reasoning_content`，
> 除非后面有一条 user 消息把它的段关掉。**

于是在任何「带工具的 agent 循环」里，**模型在一轮进行中会重读自己过去的推理**；
而且只要客户端不把它折叠掉，这一轮接一轮地读下去。两个后果：

1. **成本。** 实测：**每次请求约 28 万 token**，其中绝大部分是缓存读取，读的是累积下来的推理。
2. **一条自我条件化的通道。** 留存的不仅是过去那些轮的**结论**（那些本来就在可见的回复里），
   还有**产生那些结论的推理过程**。对一个已知会「反刍」的模型来说，那意味着要重读大量自己的思考。

相关的已发表结论是 *DeepSeek-R1 Thoughtology*（[arXiv:2504.07128](https://arxiv.org/abs/2504.07128)），
它给这件事命名并做了量化：

> 我们发现 DeepSeek-R1 有一种倾向：**反复反刍已经探索过的问题表述**，从而阻碍进一步探索。

他们对「反刍」的操作性定义值得引用，因为**它直接可测**：推理链的 **5-gram 重复率**
（他们图 3.3b 按任务画出来，范围 0–35%；本文下面的数字在计数前**去掉了空白**，见 §2 的配对表）。
他们还指出：**「在重构上花的时间长，并不必然意味着反刍多」** —— **时长不是信号，重复才是。**

### 这里的哪些结论站得住、哪些站不住

`tools/rumination_compare.py --session <id>`（它数的是**所有被重试的尝试**，
不只 `EMPTY_RESPONSE`；这个会话里 31 次中有 29 次是 `EMPTY_RESPONSE`）：

| 比较 | 被吞 | 成功 |
|---|---|---|
| 全量数据 · 链长中位数 | 2,431 字 | 2,557 字 |
| 全量数据 · 5-gram 重复率 | **20.7%** | 13.5% |
| **同一步内配对**（13 对）· 重复率 | **20.7%** | **20.8%** |
| **同一步内配对**（13 对）· 链长 | 2,526 字 | 2,167 字 |
| 同一步内配对 · 全部七项指标 | 见下 | 见下 |

* **同一步内配对**（同一个输入、不同的抽样）：**没有一项能把两者分开。**
  `rumination_compare.py` 对每一对的两个成员各算**七项指标** —— 链长、行数、
  最长连续重复行、尾段重复占比、20 字片段重复率、5-gram 重复率（论文的反刍度量）、
  以及自我指涉词密度 —— 然后报告有几项的差异超过较大中位数的 20%。实测：**7 项里 0 项**。

  有两处口径必须说明，而不是默认：**每个（会话, 轮, 步）只取一对，用第一次被吞的那次尝试** ——
  有一步被吞了 6 次，三步各 4 次，另两步各 2 次（35 次尝试落在 19 个步上）；
  改成取**最后一次**，行数一样但数值会变，而**那正是让读者怀疑这张表算错了的东西**。
  另一处：**5-gram 和片段重复率是去掉空白之后算的**，这个选择在这里值约 8 个百分点
  （去空白 20.7 / 20.8，不去 28.3 / 28.8 —— 两者都支持同一个结论，
  但独立实现的人需要知道这些数是用哪种口径产生的）。

  ```
  指标                    被吞      成功    分得开？
  chars                    2526.00     2167.00          no
  lines                      85.00       97.00          no
  max_line_run               32.00       35.00          no
  tail_repeat_%             100.00      100.00          no
  shingle20_%                 7.02        6.25          no
  ngram5_%                   20.68       20.78          no
  selfref_per_1000            0.58        0.60          no
  ```

  七项里有两项在这份数据上是**退化的**，列出来只为完整：`tail_repeat_%` 在**两组都是约 100**，
  因为每条链的尾巴都是同一个短的自我催促循环；而 `max_line_run`（约 32 vs 约 35）
  **就是那个循环** —— 成功的链里也有，**这正是它不能当探测器的原因**。
  自我指涉词表是**跟语言绑定的**（这里是中文）；换语言要用 `--self-ref-words` 传自己的词表，
  否则那一行会报约 0，看起来像个干净的负结果，而其实只是词表不匹配。

  **这是本文最强的单个结果**：**在可见的链这一层，没有任何预警信号**。「重抽一次」才是解决它的办法。
* **全量数据**：被吞的上下文里，自我指涉措辞的密度高约 **1.6–3.3 倍**，推理重复高约 **1.6 倍**。
  这说的是**哪一类对话更容易吞** —— 长的、反思性的、自我指涉的 —— **而不是哪一次尝试会失败**。

所以：**话题决定概率，抽样决定这一次。** 人们最先想到的两个机制都被测过并否掉了：
不是「它想太多所以写不完」（被吞的链并不更长，常常更短），
也不是「上下文太大了」（被吞那几步的上下文**更小**，而且在上下文压缩之后没有聚簇）。

## 三、收窄回填

**如果预测不了，退一步就是改变它发生的条件** —— 而回填这条通道，是客户端真正控制得了的那个条件。

### 先探针：文档里那个「必须」真的被强制吗？

> ⚠️ **本节已更正（2026-10-12）。** 英文版 `README.md` 是准本，更正以它为准；
> 下面这段中文是**重新对过**的，不是原译文。

文档威胁说，不完整回传推理就返回 400。这句话决定客户端**有没有资格**把过去的推理折叠掉。
于是我们测了它 —— `probes/probe_backfill_position.py`，六次请求（重跑很便宜）：

```
A 普通轮，剥掉                              HTTP 200
B 工具轮，在【活跃段】，剥掉                HTTP 400   ← 文档是对的
C 工具轮，在【过去的段】，剥掉              HTTP 200   ← ……但只在这儿
D 工具轮，在活跃段，回填                    HTTP 200   （B 的对照）
E 两工具步的段，把【较早那步】剥掉          HTTP 400   ← 这条规则不能再收紧
F 两工具步的段，两步都回填                  HTTP 200   （E 的对照）
```

**B 和 C 只差最后一条 user 消息**，就这一条把 400 翻成 200。所以那个要求是真的、
是按单条消息算的、而且**以「段」为界**：

> **带 `tool_calls` 的 assistant 消息必须带 `reasoning_content`，
> 除非后面有一条 user 消息把它的段关掉。段开着的时候，
> 这一段的*每一条*工具调用消息都得带上 —— 不只是最后一条（E）。**

这正是第三版实现的那条规则 ⇒ **收窄是合法的**；而 E 说明它同时也是**最紧的合法规则**
—— 不能再收成「只留最后一次工具调用」。两件事要跟着说清楚，因为这里都先错了一遍：

* **本注更早的草稿写的是「服务端没有强制」。** 那个结论来自
  `probes/probe_backfill_enforcement.py`，而它那条工具轮消息**压在一个更晚的 user 轮后面**
  —— 也就是说，它测的正好是**被允许**的那一格。探针对它自己那份请求没判错，
  **错的是从它推出「服务端不管」这个结论。** 旧探针留在仓库里当错误的记录，文件头现在指过来。
* **「请求里有 `tools` 参数」和「消息里有 `tool_calls`」是两回事**，而且两个都不是那条要求本身。
  真正的判据是**消息字段 + 有没有 user 轮把它的段关掉**。

边界照说：一个模型、一个端点、一天、每格 n=1。这不表示这个字段将来一定还是可选的 ——
**保留 `--revert` 那条退路。**

### 三个设计，其中两个败在结构上

值得记下来，因为这两个坑都很容易踩进去：

**v1 ——「本回合调过工具就回填」。** 这个判据**在一轮之内就会翻面**：

```
step 1（还没调工具）  142,563 token
step 2（调过工具了）  311,237 token     +16.9 万，发生在一次回答的中途
```

两个问题。它**把 KV 缓存的前缀劈成两半**，于是第二次请求基本要重算；
而且它在一次回答的中途，改变了模型**看得见自己多少**。
还有一个 bug：段中间任何一条用户消息都被当成了轮边界，让模式来回翻
（`324,393 → 150,120 → 326,701`）。

**v2 ——「每段决定一次，看上一段」。** 不翻面了，但判据和这一段实际做的事**相反**：

```
段数：678   （段 = 上一条最终回答之后的全部消息）
错：  184  = 27.2%
  上一段用过工具 / 这一段没用  → 回填开着   92
  上一段没用     / 这一段要用  → 回填关着   92
```

**而这是结构性的，不是实现疏忽**：要让模式在一段内保持不变，你必须在**段开始时**就选定它 ——
而那一刻这一段还没发生，**只有上一段可看**。
（和替代方案比：恒开正确率 59.9%，恒关 40.1%，看上一段 72.8%。
明显更好 —— **也明显仍然有四分之一的概率是错的。**）

**v3 —— 去掉全局开关，改成逐条消息判定。** 这就是补丁实现的规则：

> **只有「当前段里带工具调用的助手消息」保留推理；更早的一律剥掉。**

* **不需要预测** —— v1 和 v2 的分歧整个消失了；
* **那个昂贵的翻面消失了**：一轮之内 payload 只增不减（实测连续 16 步，每一步的增量都为正），
  而 v1、v2 是每轮在两种大小之间来回两次 —— 每次来回都让缓存前缀作废
  （具体数字见下面的**实测效果**，也包括**哪些东西并没有归零**）；
* **燃料砍在最肥的地方**：长的、反思性的推理都落在段的**最终回答**那一侧，**一条都不进历史**。

**推理到底活多久 —— 要说准。** 因为**段边界就是最终回答**，下一轮开始时，
上一轮的所有消息都在 `segStart` 之前。所以：

> **推理只活一轮。** 它在本轮的工具步里保留（工具循环因此还留着「我为什么调这个」的工作记忆），
> 而在更早的每一轮里都被剥掉 —— **包括那些轮的工具步。**

本文早先的草稿说模型「还能看见上次为什么去查东西」。**那是错的**，
而且它影响你预期能看到什么：这个设计里**没有跨轮的工具推理连续性**。
如果一个任务跨好几轮、用户说「继续」，模型是从**可见的回复和工具结果**重新推出计划的，
不是从它上一轮的推理。**这是这笔交易的成本侧**，也正是 §4 那个测量要盯的东西。

直接实测（两轮的序列，第一轮有工具步）：

```
第 1 轮进行中   [工具步, 最终回答]              → 工具步的推理**保留**（segStart = 0）
第 2 轮开始     [t1工具步, t1回答, t2工具步]    → false, false, **true**
```

### 实测效果

**不要引用单个「之前」的数字。** 补丁前的请求大小是**双峰**的，不是平的：
它在相邻轮之间（有时甚至**在一轮之内**）在约 143k 和约 357k 之间来回。
对那段时期取平均，**哪个模式都不描述**。要测就测**同条件配对** —— 相邻两轮、同一会话、中间隔着那次重启：

```
turn 698（v3 前最后一个完整轮，工具密集）  step 1   357,268
                                          step 2   359,555
turn 699（v3 下第一个完整轮，16 步）       step 1   166,777
                                          step 2   167,253
                                          …
                                          step 16  189,916
```

也就是：**在同一位置，约 357k → 约 167k**（大约一半），
而且一轮之内的增长从锯齿变成了单调：

```
补丁前，一轮：  142,563 -> 311,237     （中途 +168,700，来回两次）
补丁后，一轮：  166,777 -> 189,916     （16 步共 +23,139，从未为负）
```

`tools/prefix_switch_report.py` 直接测那个翻面：数**比前一次小**超过某个阈值（默认 10,000 token）的请求，
排除掉**压缩事件之后的第一次请求**（压缩合法地把 payload 砍掉 —— 记录到的一次是 792k → 16k；
那是客户端主动丢弃历史，不是前缀切换）。
排除用的是那个**确切位置**，不是一个时间窗：窗口开得够宽（30 分钟）会把压缩之后真正发生的翻面一起吞掉；
开得窄（2 分钟）又会在你压缩后离开十分钟时漏掉同一次合法的缩小。
在本次部署上实测：22 次排除**全部**落在压缩后 87 秒内，**且全部是压缩后的第一次请求** ——
所以这个确切判据复现了窗口猜对的每一个案例。

表里最后一行在一轮还在进行时是**暂定的** —— 档案是追加写的，正在进行的轮会继续追加，
所以最新那个边界的数还会变（实测：某个边界在写一半时读到的值比它稳定后小）。
引用它之前，等这一轮结束再跑一次。

```
判据：totalTokens(N+1) - totalTokens(N) <= -10,000
一个会话，2026-09-23，扫了 112 次请求 → 7 次缩小

11:32:31  turn 684   310,072 -> 142,563   (-167,509)   \  补丁前：payload
11:33:10  turn 685   311,237 -> 143,098   (-168,139)    |  反复减半又翻倍，
11:47:15  turn 691   318,616 -> 147,670   (-170,946)    |  每轮两次
11:48:36  turn 691   324,393 -> 150,120   (-174,273)    |
12:07:08  turn 694   341,727 -> 159,025   (-182,702)   /
12:41:48  turn 699   359,555 -> 166,777   (-192,778)   ← v3 生效；第一次请求
                                                          把全部历史剥掉（一次性）
13:05:15  turn 700   189,916 -> 179,907    (-10,009)   ← 轮边界：上一轮的
                                                          工具推理离场
```

**关于那个「零」，要说准。** 「前缀切换降到 0」是错的 —— 本文早先的草稿就这么写过。实际发生的是：

* **轮内翻面没了** —— 一轮之内 payload 只增不减（实测 16 步，每一步增量都为正）。
  那才是昂贵的故障模式：每轮两次 ±17 万的翻面，每次都让缓存前缀作废；
* **每个轮边界仍有一步小幅下移**，大小等于上一轮工具步的推理量
  （实测：−10,009、−1,967，然后是 +292 和 +214 —— 后两次是新的用户消息盖过了剥掉的推理）。
  这一步对**任何剥掉过去推理的规则**都是**固有的**：段边界一过，那些消息就变了，
  缓存前缀到此为止。它是每轮一步，而不是两次大翻面，而且**上界就是那一轮产生了多少推理**。

**大约省一半 token**，没有观察到任务连续性受损。

## 四、副作用，和它的尺子

剥掉过去的非工具推理，意味着模型不能再重读它。可能的代价是**重复劳动** ——
重读一个已经读过的文件、重跑一条已经跑过的命令、重新推导一个已经有结论的东西。
**这件事可测，而这是唯一让这个风险可以被接受的理由。**

`tools/repeat_labor_report.py` 为每一次工具调用构造一个键（工具 + 参数），然后报两个数。
**只有其中一个能当趋势用**，而这一点很容易搞错：

| 数 | 是什么 | 能当趋势吗 |
|---|---|---|
| **组数（groups）** | 出现在不止一个段里的键 | **不能。** 组是整段历史的属性，总数随档案增长而增长，于是它会「永远在涨」 |
| **回头调用 / 每千次调用** | 一次调用的键**在同一会话更早的段**里已经出现过 | **能。** 分母是当天的调用数，档案增长不会推动它 |

```
扫过的工具调用：16,887
  同段内                    : 184   （复查，不计）
  跨段 · 同窗口             : 244   ← 存量，不是趋势
  跨段 · 全局               : 1525  （旧口径；把两个窗口各读同一个文件一次
                                      也算成一次「重复」）
  扣掉的轮询命令            : 4

每千次调用里的回头调用        : 91.3

按天（回头 / 调用 = 每千次）：
  09-17    3/154  =  19.5      09-21  108/1110 =  97.3
  09-18    1/72   =  13.9      09-22   48/843  =  56.9
  09-19    0/62   =   0.0      09-23   13/281  =  46.3
  09-20   28/746  =  37.5
```

**跨天的速率不能直接比** —— 那张表在两周里从 0 到 232（每千次）。
要比就得让**工作种类**保持不变：一天都在读文件，天生就高；一天都在跑命令，天生就低。所以：

* 比**同条件的窗口**（同一会话、类似的工作），别比随便两天；
* 优先用「改动前后」这一对，而不是一整条时间序列。

还要修正本文早先草稿里的一处：它把补丁前那个速率的下降解释成「采样结构变了」——
说是几个会话分支共用一段历史，同一个重复被各数了一次。
**那个解释经过测试，不成立**：只看单个分支自己的速率，这个序列不是单调的
（从 09-10 到 09-19 由 136 降到 0，然后 09-20 到 09-22 又升到 107–221），
而分支稀释产生不了那个回升。**这里把它记为「待解释」，不是结论。**

做这个instrument 的路上踩了三个坑，每一个都产生过**很有把握的错误读法**：

* **把键全局分组**：两个窗口各读同一个文件一次，被算成一次「重复」。
  那是两个 agent 各干各的活，不是同一个 agent 在重复自己 —— 它把数放大了约 6 倍（1,524 vs 244）。
* **一张按天的表，把「跨天」的功劳记给除最后一天以外的每一天。**
  于是**任何一组的最后一天永远拿不到这一格**，**新发生的重复被记到旧行上** ——
  一张不管发生什么都会读成「越来越糟」的表。（真实存在的一组横跨 09-11 … 09-23，被记到了 09-11。）
  已换成按天的速率。
* **一个什么都没匹配上的轮询过滤器。** 正则结尾写成了字面的 `\b` 而不是词边界（所以连 `ls -la` 都匹配不上），
  又被 `^` 锚住（漏掉最常见的 `cd x && ls` 写法），它那条 curl 分支还要求 `/dev/null` 出现在固定位置。
  「扣掉的轮询命令：0」这行字，其实是**一步没跑**被当成了一个发现。

推荐用法：先定一个基准，然后每隔几天用 `--since <上次时间点>` 跑一次，
**比速率，不要比总数**。

```
基准（改动前，单会话）：50 组跨段重复
每隔几天：--since <上次检查时间>  →  读「每千次调用里的回头调用」
```

**当趋势读，别当判决读**：同一个文件读两次不自动等于浪费（它可能变了，也可能是有意的复查）。
这里数的是**痕迹**；它们是什么意思由人来判。
**如果部署 `patch_backfill.py` 之后这个速率往上走，就回退。**

## 五、怎么用这些零件

```bash
# 1. 测你自己的模型/端点上，API 还容不容忍收窄后的回填
DEEPSEEK_API_KEY=sk-... python3 probes/probe_backfill_position.py

# 2. 看你自己的被吞回复
python3 tools/silence_shape_report.py --shape            # 每次尝试的形状
python3 tools/silence_shape_report.py --watch            # 记下「整轮没产出」的回合

# 3. 把收窄后的回填打到 DeepSeek Harness 上（需要重启）
python3 patches/patch_backfill.py --check
python3 patches/patch_backfill.py
python3 patches/patch_backfill.py --revert               # 撤销

# 4. 盯副作用
python3 tools/repeat_labor_report.py

# 5. 数 payload 缩小（前缀作废）的次数
python3 tools/prefix_switch_report.py

# 6. 比较被吞与成功两次尝试的链
python3 tools/rumination_compare.py --session <id>
```

这个补丁针对 `@deepseek-ai/dsh-llm-deepseek`，**如果它需要的锚点移位了，它会拒绝执行**。
它也**拒绝猜**：每一处替换必须精确命中一次，改完还会做语法检查，不过关就自动回滚。
vendor 补丁会被 `npx` 升级覆盖 —— 那是它的正常失效方式，而**在一个定时任务里跑 `--check` 是便宜的守卫**。

覆盖规则，优先级从高到低：

| 控制 | 效果 |
|---|---|
| `~/.dsh/backfill_mode` = `on` / `off` / `auto` | 强制模式，用于 A/B 对照 |
| 用户消息开头的 `【工作】` / `【聊天】` | 按段覆盖；发出去之前会被去掉 |
| 规则本身 | 逐条消息判定，如 §3 所述 |

### ⚠️ 信任何一个数之前：档案代次的坑

这里每个工具都读 DSH 的会话档案。**DSH 迁移会话格式时改了档案文件名，而它不删除、
也不重写旧文件** —— 它在旧的 `session.v3.jsonl.zstd` 旁边发一个新的
`session.v4.jsonl.zstd`，旧那个就冻结在迁移那一刻。于是任何**写死了代次名**的脚本
**照样返回数据、照样退出码 0，却静默地不给你任何新东西。**

这不是假设。2026-10-12 在同一台机器上重跑同一个工具，**只改它打开的文件名**：

```
写死 `session.v3.jsonl.zstd`  ->  111 条被吞的回复，最新到 09-27
用实际存在的最新代次           ->  152 条被吞的回复，最新到 10-10
```

**41 条被吞的回复是隐形的 —— 不报错、不告警。** 那个 v3 文件甚至还在、还能解析，
它只是一个月前就冻住了。任何从旧代次上读出来的「最近好像变好了」或者
「<某日>之后没再出过事」，都是文件名的产物，不是发现。

`tools/dsh_archive.py` 是唯一决定打开哪个文件的地方；各工具从它 import
`latest_for()` / `iter_archives()`，而不是自己写文件名。就算你不用这个仓库，
里面两条规矩也值得抄：

* **按版本号取最高代次。** `sorted(glob(...))[-1]` 是按文件名字典序比的 —— v3 对 v4
  碰巧能用，而出现 v10 的那天会**静默地坏掉**。
* **档案代次不是身份。** 迁移会为每个被打断的轮补一条合成的 `turn/end`，
  于是之后所有 `seq` 整体 +1（实测；有一份档案偏移 +2）。任何拿 `seq` 当键的东西
  —— 去重台账、「这条我见过没」的集合 —— 在代次变化时都得重新定键。**优先拿内容定键。**

你要是把这里的工具改成读自己的档案，**让工具把它打开的那个文件打印出来**，
并断言它不是旧的。这里的失败形状是：一个**自信、格式完好、但停在了一个月前**的答案。

## 六、我们还不知道什么

* **为什么正文块从不打开。** 最贴近的描述是「在正文本该开始的那个边界上，抽样回落进了推理块，
  然后一路循环到结束」。**那是描述，不是解释。** 重试有效，说明那个边界是一个对抽样敏感的位置 ——
  但这里没有任何东西指认出原因。
* **收窄回填是否真的降低了失败率。** token 上的效果立刻可见而且很大；失败率上的效果需要几周的流量。
  基准大约是已交付回复的 3%，而且是突发式分布，所以**几个安静的日子什么都证明不了**。
  （早期信号，明确不算证据：部署之后两分钟有一次被吞，其后的 78 分钟密集用工具期间一次都没有。）
* **`reasoning_content` 这个要求，在别的模型和供应商上是什么样。** 一个 200 就只是一个 200。
  如果你依赖收窄后的回填，**去探你自己的端点** —— 并且留着那条回退路。
